# M1: Engine, Spec Doctor, Reference, Samples, Markdown Twins, `llms.txt`

Status: agreed scope, 2026-11-27. No code exists yet. Owner: product manager. Open questions 1 to 3
were settled on 2026-11-27 and are recorded at the end.

Source of milestone boundaries: `docs/product-brief.md`, "Milestones". Where a statement below rests
on a research finding it cites the finding by its name in the brief's table. Everything else is
marked **[judgment]** and is the product manager's call, not evidence.

## What M1 is for

One spec in, one correct portal out, on one machine. M1 proves the two things nothing later can fix:
that the reference and samples are right on real, messy specs, and that the spec doctor finds the
defects that make calls fail. There is one implicit tenant, one default theme and no server.

Positioning, so effort goes to the right place:

- **Table stakes in M1** (brief, "Table stakes"): OpenAPI-driven reference, multi-language snippets,
  `llms.txt`, Markdown page variants. These must be correct. They are not where we win.
- **Differentiator in M1** (brief, "Open differentiators"): spec repair. Most of the discretionary
  effort in M1 belongs to the spec doctor and to sample correctness, which is the groundwork for
  "samples tested against the API" in M2.

## In scope

- **Engine**: pure library, no I/O. Input: one OpenAPI 3.0 or 3.1 document, already bundled into a
  single object, plus an optional doctor patch. Output: normalized model, reference page models,
  code samples, Markdown twins, `llms.txt` and spec-doctor findings.
- **Spec doctor**: findings and proposed fixes for security schemes, servers, examples and
  operation ids. Output is a machine-readable report and a patch that the engine accepts as input.
- **API reference**: one page per operation, grouped by tag, with parameters, request body,
  every documented response and security requirements. **[judgment]** One page per operation,
  not one long page per tag: it is what makes per-page twins, deep links and large specs tractable.
- **Code samples in 8 languages**, generated for every operation, with a language switcher.
- **Markdown twin** of every reference page, and one `llms.txt`.
- **Minimal renderer**: static output, one default theme (light), left navigation, operation pages,
  a read-only doctor report page. Spec supplied as a local file by a build command.
- **Fixture corpus** used by every criterion below, in `fixtures/specs/` (see its `README.md` for
  sources, pins and hashes): 12 committed specs including Petstore (3.0, 19 operations), Redocly
  Museum (3.1, 8), Adyen Checkout (3.1, 31) and OpenAI (3.0, 148); four fetch-only specs downloaded
  by `fixtures/specs/fetch.sh`, namely Clubhouse (3.0, 41, no `operationId`s), Stripe (3.0, 612),
  GitHub Enterprise Server 3.9 (3.0, 908) and GitHub's 3.1 description (1,281); and 16 malformed
  specs in `fixtures/specs/malformed/`, which are the `broken` set named below. One fixture is
  still to be written by QA: `hard-schemas`, a small spec built to exercise `oneOf`, `anyOf`,
  `allOf`, discriminators and mutual recursion in a committed file.

## Out of scope

Each of these is tempting. Each has a milestone, or is cut.

| Tempting thing | Where it belongs |
|---|---|
| "Try it" console, request proxy, any live call from the portal | M2 |
| API MCP | M2 |
| Samples executed against the customer's real API | M2 (M1 executes against a local mock only) |
| Credential entry of any kind; samples filled with a real key | M2 |
| Brand extraction, theme editor, more than one theme | M3 |
| Dark mode and dark-mode polish | M3. M1 tokens must not prevent it; M1 ships light only. **[judgment]** |
| Dashboard, sign-in, projects, spec upload UI, Git sync, publish pipeline | M4 |
| Accept/reject UI for doctor fixes | M4. M1 applies fixes from a patch file. |
| Hostname-to-tenant resolution, multi-tenant storage | M4 |
| Search of any kind, including client-side and a search index shipped to the browser | M5 |
| Guides ingestion and rendering, `op:` link resolution from guides, guide back-links | M5 |
| Docs MCP | M5 |
| Custom domains, billing, analytics | M6 |
| Swagger 2.0 input | Not planned. Rejected with a clear message. Settled 2026-11-27. |
| Webhooks and callbacks pages | Not in M1. Listed by the doctor as "not rendered". **[judgment]** |
| `llms-full.txt`, AI chat, changelog, versioned docs, i18n | Not planned in any milestone yet. |
| LLM-written descriptions or examples | Not planned. Doctor fixes in M1 are rule-based so output stays deterministic. **[judgment]** |

Two M5 items constrain M1 even though they are out: the engine may define the search-index output
shape, but nothing consumes it; and operation ids and URLs chosen now are what guides will link to
(criteria 11 and 12).

## Acceptance criteria

26 criteria. Each is one sentence, tagged with the user it serves. "QA" and "DX" say who checks it.
"All fixtures" means the fixture sets listed above, excluding `broken` unless named.

### Reference quality

1. **[reader]** On `hard-schemas`, every `oneOf` and `anyOf` renders as a set of named variants the
   reader can switch between, each showing its own properties, and a discriminator shows its
   property, its allowed values and which variant each value selects. Answers: "`oneOf`/`anyOf`
   render badly". QA.
2. **[reader]** On `hard-schemas`, `allOf` is shown as one merged property list, and a
   self-referencing or mutually recursive schema renders to a finite page whose recursive property
   is expandable on demand, with the build terminating. Answers: "`oneOf`/`anyOf` render badly"
   (same class of schema-rendering defect; the recursion part is **[judgment]**). QA.
3. **[reader]** Every operation page in all fixtures shows, for each parameter and body property,
   its name, type, required or optional, default, every enum value and stated constraints, and
   shows every documented response including 4xx, 5xx and `default` with its status, description
   and schema. Answers: "Errors, enums and edge cases are undocumented" (low confidence). QA, by
   comparing page models to the spec.
4. **[reader]** Every operation page states which credential the call needs, where it goes (header,
   query or cookie, with the exact name) and any scheme prefix such as `Bearer`, or says plainly
   that the spec does not declare one. Answers: "The spec itself is wrong" (security schemes,
   headers and token prefixes). QA.

### Invalid and thin specs

5. **[buyer]** Given a document that is not parseable or is not OpenAPI 3.0 or 3.1 (including
   Swagger 2.0), the build fails without writing a portal and reports what is wrong and where, by
   line or JSON pointer. QA, on `broken`.
6. **[buyer]** Given a parseable spec with local defects (an unresolvable `$ref`, an invalid schema,
   an example that violates its schema), the build completes, every unaffected operation renders in
   full, and each defect appears as a doctor finding with a JSON pointer. QA, on `broken`.
7. **[reader]** Where a spec gives no example, sample values are synthesized from the schema and
   satisfy its type, format, enum and constraints (an `email`-format string looks like an email,
   not `"string"`), and the doctor report lists which operations use synthesized values. Answers:
   "Examples are absent or do not run". QA, by validating every synthesized value against its
   schema.

### Spec doctor

8. **[buyer]** The doctor reports every operation with no effective security requirement, every
   reference to an undefined security scheme, a spec that defines no schemes, missing `servers`,
   relative, non-HTTPS, localhost or placeholder server URLs, and server variables without
   defaults. Answers: "The spec itself is wrong". QA, on `broken` and all fixtures.
9. **[buyer]** The doctor reports parameters and request bodies without examples and operations
   with missing or duplicate `operationId`s, and does not report as a defect an `operationId` that
   merely contains unusual characters such as `gists/create`. Answers: "Examples are absent or do
   not run". QA.
10. **[buyer]** Every finding has a severity, a JSON pointer, a one-sentence explanation of the
    consequence for a reader, and either a patch that fixes it or a statement of the one fact the
    buyer must supply; applying all offered patches and rebuilding removes exactly those findings
    and introduces none. Answers: "The spec itself is wrong" (small spec fixes raise call success).
    QA.

### Operation ids and deep links

11. **[reader]** Every operation, every response status on an operation page and every top-level
    schema section has its own URL or fragment, which loads directly to that content, and those URLs
    are identical across rebuilds of an unchanged spec and unchanged when unrelated operations are
    added. QA.
12. **[reader]** An operation with no `operationId` gets the derived id "method, then the path with
    every non-alphanumeric character replaced by `_`" (`get` + `/payments/{id}` gives
    `get_payments__id_`), so that all 41 Clubhouse operations and every GitHub id containing `/`
    have a working page and URL, and two operations that would share an id are resolved exactly as
    section 1.1 of `docs/contracts/guides-contract.md` specifies (a `_2`, `_3` suffix in a defined
    order), with each collision reported as a doctor finding naming both locations. QA, against
    the worked examples in that section.

### Code samples

13. **[reader]** For every operation in all fixtures and each of the 8 languages, the sample passes
    that language's own parser or compiler syntax check. Answers: "Examples are absent or do not
    run". QA. **[judgment]** This needs 8 toolchains in CI; that cost is accepted.
14. **[reader]** For a fixed matrix of request shapes (path, query and header parameters; JSON,
    form-urlencoded and multipart bodies; bearer, basic, and API key in header and in query), the
    sample in each of the 8 languages, run unmodified against a local mock, sends the expected
    method, URL, headers and body. Answers: "Examples are absent or do not run". QA.
15. **[reader]** Every sample uses the first declared server URL and a visibly named credential
    placeholder in the position and with the prefix the security scheme requires, and no sample or
    page in the output contains a real credential or accepts one. Answers: "The spec itself is
    wrong" (token prefixes). QA, plus security reviewer.
16. **[reader]** Choosing a sample language on one page shows that language on every other page and
    after a reload and in a new tab, with no server state, and with JavaScript disabled every page
    still shows a readable sample in the default language. QA.

### Agents: Markdown twins and `llms.txt`

17. **[reader, agent]** Every reference page has a Markdown twin at the page URL plus `.md`, linked
    from the page, containing the same parameters, schemas, responses and security statement as the
    HTML page and one sample (cURL) with no HTML or navigation chrome, and `llms.txt` at the portal
    root lists every page once with its title, description and a resolving link to its twin.
    Answers: "`llms.txt` is rarely fetched" (per-page Markdown carries the agent traffic). QA, by
    diffing twins against page models. **[judgment]** `llms.txt` is table stakes: it must exist and
    be correct, and gets no effort beyond that.
18. **[reader, agent]** Given only the twin of one operation from Petstore and one from Museum, and
    a placeholder credential, an AI agent writes a request that the local mock accepts on the first
    attempt. DX.

### Safety of rendered content

19. **[buyer]** Spec text containing HTML, script, event handlers or `javascript:` URLs, in any
    description, summary, example, enum or name, appears in pages and twins as inert text and
    executes nothing. Standing constraint: tenant content is never executed. QA on a `broken`
    fixture; security reviewer sign-off is required.

### Determinism and static output

20. **[buyer]** Building the same spec and patch twice, on two machines, yields byte-identical
    pages, twins, `llms.txt`, samples and doctor report, with no timestamps or random ids in the
    output. QA.
21. **[buyer]** The built portal is a directory of static files that works from a plain file server
    with no application server, both at the root and under a subpath such as `/docs`, with every
    internal link, asset and twin URL resolving in both. Standing constraint: static export;
    decision: subpath hosting. QA. **[judgment]** Checking the subpath now is cheaper than
    retrofitting it in M4.

### Accessibility

22. **[reader]** On a fixed sample of pages (a simple operation, a `hard-schemas` operation, a tag
    index, the doctor report), an automated WCAG 2.2 AA audit reports zero violations, and
    navigation, the language switcher, variant switchers, schema expanders and copy buttons are all
    operable by keyboard alone with a visible focus indicator. QA, with a manual screen-reader pass
    by UX on the same pages. **[judgment]** AA is our bar; the brief does not set one.

### Performance on a very large spec

23. **[buyer]** The GitHub fixture (908 operations) and the Stripe fixture (612) each build to a
    complete portal, every operation present, within 5 minutes on the CI machine, with the engine
    pass alone under 60 seconds. QA. **[judgment]** Thresholds are provisional; the architect
    should confirm or replace them before work starts.
24. **[reader]** On the GitHub fixture, no operation page transfers more than 500 KB compressed
    excluding fonts, no page embeds the whole spec, and the navigation listing all 908 operations
    responds to scroll and click without a visible stall on a mid-range laptop. QA for the first two
    clauses, DX for the third. **[judgment]** Threshold provisional, as above.

### End to end

25. **[reader]** Starting from the Petstore portal's home page with no prior knowledge of the API, a
    developer finds an operation, finds what credential it needs, copies a sample in a language of
    their choice, and has it run against the local mock after changing only the credential
    placeholder. DX, repeated in at least three of the 8 languages.

### Published spec

26. **[buyer]** The build writes the published spec beside the portal as `spec/openapi.json` or
    `spec/openapi.yaml`: byte-identical to the input when no fix is applied, and otherwise the
    patched document, with the model recording the hash of the fetched and of the published bytes,
    and with every operation id unchanged by applying an `operationId` fix. Decision: guides are
    generated from the patched spec. QA, on all fixtures with and without the doctor's patches.

## Definition of done

M1 is complete when all of the following are true. This follows `CLAUDE.md`, "Rules for using the
team".

1. **PM criteria checked.** The product manager has marked each of the 26 criteria met, not met or
   not checked, with what was looked at, against the built portals, not a summary. No criterion is
   "not checked". Any "not met" is either fixed or moved out of M1 by a recorded decision in this
   file.
2. **QA has run the tests.** The QA engineer has run the automated suite on all fixtures on CI and
   reports the result per criterion. Criteria 13 and 14 have run with all 8 toolchains.
3. **DX reviewer has used the result.** The DX reviewer has used the built Petstore, Museum and
   GitHub portals and completed criteria 18, 24 (third clause) and 25.
4. **Security reviewer has signed off** on criteria 15 and 19, since M1 renders tenant content.
5. **Standing constraints hold**: the engine performs no I/O; core pages are static (criterion 21);
   tenant content is not executed (19); no credential is stored or logged, which in M1 means none is
   ever accepted (15).
6. `docs/product-brief.md` is updated with any decision M1 changed.

## Product questions

Settled on 2026-11-27:

1. **Which 8 languages?** cURL, JavaScript (`fetch`), Python (`requests`), Go, Java, C#, PHP, Ruby.
   The HTTP client each emitter targets is listed in ADR 0005.
2. **Swagger 2.0** is out for now. It is rejected with a clear message.
3. **Derived operation ids.** The rule is section 1.1 of `docs/contracts/guides-contract.md`, which
   is normative for both projects. A collision is resolved by suffix and reported; it does not fail
   the build.

Still open, with the default that applies in M1:

4. **Should readers see that a sample uses synthesized values?** Criterion 7 tells only the buyer,
   through the doctor report. The guides module found placeholder values on 85 of Stripe's 120 guide
   pages, so on specs like that a reader-visible marker would appear on most pages. Default: buyer
   only in M1.
