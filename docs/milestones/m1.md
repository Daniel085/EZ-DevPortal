## What M1 is for

One spec in, one correct portal out, on one machine. M1 proves the two things nothing later can fix:
that the reference and samples are right on real, messy specs, and that the spec doctor finds the
defects that make calls fail. There is one implicit tenant, one default theme and no server.

Positioning, so effort goes to the right place:

- **Table stakes in M1** (brief, "Table stakes"): OpenAPI-driven reference, multi-language snippets,
  `llms.txt`, Markdown page variants. These must be correct. They are not where we win.
- **Differentiator in M1** (brief, "Open differentiators"): spec repair. Most of the discretionary
  effort in M1 belongs to the spec doctor and to sample correctness, which is the groundwork for
  "samples tested against the API" in M2.

## In scope

- **Engine**: pure library, no I/O. Input: one OpenAPI 3.0 or 3.1 document, already bundled into a
  single object, plus an optional doctor patch. Output: normalized model, reference page models,
  code samples, Markdown twins, `llms.txt` and spec-doctor findings. The M1 CLI reads exactly one
  local file and follows no `$ref` to another document (see "Out of scope").
- **Spec doctor**: findings and proposed fixes for security schemes, servers, examples and
  operation ids. Output is a machine-readable report and a patch that the engine accepts as input.
  It also decides whether each server is callable by the proxy (ADR 0004, `server-not-callable`),
  using a snapshot of the Public Suffix List vendored as data under the licence exception in the
  brief, and offers the allowed-hosts fix for an open host variable. The proxy that enforces the
  result is M2.
- **API reference**: five kinds of page and no others (ADR 0003, "Pages and paths"): a home page,
  one page per tag, one page per operation, one page per named schema, and the doctor report. An
  operation page shows parameters, request body, every documented response and security
  requirements. It shows in place up to 32 of the named schemas it refers to, nearest first
  (`pageSchemas`, ADR 0003, "Budgets"); every other named schema it refers to is a link to that
  schema's own page. **[judgment]** One page per operation, not one long page per tag: it is what
  makes per-page twins, deep links and large specs tractable. Schema pages are in M1 because
  showing every schema an operation reaches on the operation's page is not viable. Evidence, the
  architect's measurement in ADR 0003 and not re-run by the product manager: every Stripe
  operation reaches about 1,060 named schemas, 1.2 MB as written; no GitHub operation reaches more
  than 62.
- **Code samples in 8 languages**, generated for every operation, with a language switcher.
- **Markdown twin** of every reference page, and one `llms.txt`. "Reference page" means an
  operation, tag or schema page. The home page and the doctor report have no twin.
- **Minimal renderer**: static output, one default theme (light), left navigation, the five kinds
  of page above, the doctor report read-only. No dark mode and no search of any kind. Spec
  supplied as a local file by a build command.
- **Fixture corpus** used by every criterion below, in `fixtures/specs/` (see its `README.md` for
  sources, pins and hashes).
  - **Exists.** 12 committed specs including Petstore (3.0, 19 operations), Redocly Museum (3.1,
    8), Adyen Checkout (3.1, 31) and OpenAI (3.0, 148); four fetch-only specs downloaded by
    `fixtures/specs/fetch.sh` into `fixtures/specs/large/`, namely `clubhouse.yaml` (3.0, 41, no
    `operationId`s), `stripe.json` (3.0, 612), `github-ghes.json` (GitHub Enterprise Server 3.9,
    3.0, 908) and `github-api-3.1.json` (1,281); and 16 malformed specs in
    `fixtures/specs/malformed/`, which are the `broken` set named below. Five of the 16 are fatal
    and eleven build with findings (criteria 5 and 6).
  - **To be written by QA before the engine work** (kickoff, step 2). The readiness audit found
    the corpus lacks all of these, and the criterion named cannot be checked without it:
    - `hard-schemas`: `oneOf`, `anyOf`, `allOf`, discriminators and mutual recursion in one small
      committed spec (criteria 1, 2 and 22).
    - Hostile content: HTML, script, event handlers and `javascript:` URLs in descriptions,
      summaries, examples, enum values and names (criterion 19).
    - A parseable spec with an invalid schema and an example that violates its schema
      (criterion 6).
    - The request-shape matrix, a spec whose first server is the local mock, with the expected
      method, URL, headers and body of each row written by hand (criterion 14).
    - Servers with host variables, one per row of the worked-examples table in ADR 0004
      (criterion 29).
    - The local mock, which is test code as ADR 0005 defines it and not a spec, and the
      mock-server overlays for Petstore and Museum (criteria 14, 18 and 25).

## Acceptance criteria

31 criteria. Each is one sentence, tagged with the user it serves. "QA" and "DX" say who checks it.
"All fixtures" means the 12 committed specs, the four fetch-only specs and `hard-schemas`. The
`broken` set and QA's other fixtures are used only where a criterion names them. Numbers are never
reused or reordered, because other documents cite them; criteria 27 to 31 were added on 2026-11-27
and sit in the sections at the end.

Terms used below, each defined in an ADR:

- **A normal build** is a build of a spec as supplied, with or without the doctor's fixes. It is
  what a reader sees.
- **A mock-server build** is the same build with an overlay holding one hand-written patch, which
  replaces the first server's `url` with the local mock's address, `http://127.0.0.1:<port>` plus
  the server's base path (ADR 0005, "The local mock"). It exists only so that a sample can be run
  without calling a real API. Nothing else differs from the normal build.

### Reference quality

1. **[reader]** On `hard-schemas`, every `oneOf` and `anyOf` renders as a set of named variants the
   reader can switch between, each showing its own properties, and a discriminator shows its
   property, its allowed values and which variant each value selects. Answers: "`oneOf`/`anyOf`
   render badly". QA.
2. **[reader]** On `hard-schemas`, `allOf` is shown as one merged property list, and a
   self-referencing or mutually recursive schema renders to a finite page on which each reference
   to a named schema is a link or an expander leading to that schema's one section on the page or
   to its own page, never a nested copy of it, with the build terminating. Answers: "`oneOf`/`anyOf`
   render badly" (same class of schema-rendering defect; the recursion part is **[judgment]**). QA.
   Amended 2026-11-27: "expandable on demand" is now stated as ADR 0006, rule 7, defines it.
3. **[reader]** Every operation page in all fixtures shows, for each parameter and body property,
   its name, type, required or optional, default, every enum value and stated constraints, and
   shows every documented response including 4xx, 5xx and `default` with its status, description
   and schema; a property of a named schema is shown either in that schema's section on the
   operation page or on that schema's own page, which the operation page links to at the place
   the schema is referred to; every named schema has a schema page showing the same facts for
   each of its properties; and no page in any fixture is marked truncated. Answers: "Errors, enums
   and edge cases are undocumented" (low confidence). QA, by comparing page models to the spec and
   following every schema link. Amended 2026-11-27 for schema pages.
4. **[reader]** Every operation page states which credential the call needs, where it goes (header,
   query or cookie, with the exact name) and any scheme prefix such as `Bearer`, or says plainly
   that the spec does not declare one. Answers: "The spec itself is wrong" (security schemes,
   headers and token prefixes). QA.

### Invalid and thin specs

Which faults stop a build is ADR 0004, "Fatal and degrading faults": a fault is fatal only when
the engine cannot tell what the root document is. The fatal codes are a closed list of four.

5. **[buyer]** Given a root document with one of the four fatal faults, namely `parse-error` (not
   YAML or JSON, or empty), `limit-exceeded` (past a parsing limit), `not-openapi` (the root is
   not a mapping, or has neither an `openapi` nor a `swagger` key) or `unsupported-version`
   (Swagger 2.0, or an `openapi` value that does not name 3.0.x, 3.1.x or 3.2.x), the build exits
   non-zero, writes no file, leaves an output directory that already exists as it was, and prints
   each finding with what is wrong and where, by line or JSON pointer. QA, on the five fatal
   `broken` fixtures (`empty`, `invalid-yaml`, `invalid-json`, `missing-openapi`,
   `unsupported-swagger-2.0`), and on a document the test generates past a parsing limit, since
   `broken` holds none for `limit-exceeded`. Amended 2026-11-27 to name the fatal faults.
6. **[buyer]** Given a root document with any other fault, including an unresolvable `$ref`, a
   `$ref` to another document, a pure `$ref` cycle, a missing or wrongly typed node, a duplicate
   `operationId`, an invalid schema (`schema-invalid`) and an example that violates its schema
   (`example-invalid`), the build completes and writes a portal, every unaffected operation
   renders in full, and each fault appears as a warning in the doctor report with a JSON pointer.
   QA, on the eleven `broken` fixtures that are not fatal (the seven of stage `structure` other
   than `missing-openapi` and `unsupported-swagger-2.0`, the three of stage `resolve` and
   `duplicate-operation-id`), asserting the pointers in `malformed/expected.json`, and on QA's
   fixture for the invalid schema and the invalid example, which `broken` lacks. Amended
   2026-11-27 to say which faults build with findings.
7. **[reader]** Where a spec gives no example, sample values are synthesized from the schema and
   each one, checked by the engine's own validator, satisfies every keyword the validator checks:
   its type, `enum`, `const`, the numeric, length, item and property constraints listed in ADR
   0003, "Schema validation", and its `format` where the format is one of `date`, `date-time`,
   `email`, `uri`, `uuid`, `hostname`, `ipv4`, `int32` and `int64` (an `email`-format string looks
   like an email, not `"string"`); conformance to `pattern`, to `patternProperties` and to any
   other format is not checked and is reported as not checked on that value, never as satisfied;
   where no value satisfies the schema the value is still shown and the doctor reports
   `synthesis-failed`, a warning, at the schema; the doctor report lists which operations use
   synthesized values; and every page model marks each value as declared in the spec or
   synthesized, so a later feature never shows a synthesized value as a declared example. Answers:
   "Examples are absent or do not run". QA, by validating every synthesized value in all fixtures
   against its schema: each has no validation error or a `synthesis-failed` finding at its schema;
   every `synthesis-failed` in the committed fixtures is listed in a committed file with the
   reason that schema admits no value, and one not listed fails the test; and every synthesized
   value whose schema has a `pattern` or an unlisted format names it as not checked. Amended
   2026-11-27: "type, format, enum and constraints" was not true as designed, because tenant
   patterns are never executed.

### Spec doctor

8. **[buyer]** The doctor reports every operation with no effective security requirement, every
   reference to an undefined security scheme, a spec that defines no schemes, missing `servers`,
   placeholder server URLs, server variables without defaults, every server the proxy will not
   send to as `server-not-callable` (a relative, non-HTTPS or localhost URL, a variable with an
   empty `enum`, and an open host variable as ADR 0004 defines it), and every operation with a
   required controlled header as `controlled-header-required`. Answers: "The spec itself is
   wrong". QA, on `broken` and all fixtures, adding a fixture for any case the corpus lacks.
   Amended 2026-11-27 to name the two findings.
9. **[buyer]** The doctor reports parameters and request bodies without examples and operations
   with missing or duplicate `operationId`s, and does not report as a defect an `operationId` that
   merely contains unusual characters such as `gists/create`. Answers: "Examples are absent or do
   not run". QA.
10. **[buyer]** Every finding in a doctor report has a severity, which is warning or info since an
    error means no portal (criterion 5), a JSON pointer and a one-sentence explanation of the
    consequence for a reader; every warning has either a patch that fixes it or a statement of
    what the buyer must supply or change; an info finding, such as `webhook-not-rendered`,
    `callback-not-rendered` or `slug-collision`, is advice and may have neither; applying all
    offered patches, with a valid value supplied for every fix that takes an input, and
    rebuilding removes exactly those findings and introduces none, while a fix whose input is not
    supplied is not applied and its finding remains and names the input. Answers: "The spec
    itself is wrong" (small spec fixes raise call success). QA, with the input values held in a
    committed overlay file per fixture. Amended 2026-11-27 to say how a fix that needs an input
    counts, and again for findings that are advice.

### Operation ids and deep links

11. **[reader]** Every operation, tag and named schema has its own page URL, and every section of
    an operation page (`parameters`, `request-body`, `responses`, `security`, `samples`), every
    response status on it and every named schema shown on an operation or schema page has its own
    fragment; each loads directly to that content with JavaScript off; and those URLs are
    identical across rebuilds of an unchanged spec and unchanged when unrelated operations are
    added, where an added operation is not unrelated to an existing one if it takes the id or the
    slug that one had under the collision rules of contract 1.1 and ADR 0002, in which case both
    are reported as `operation-id-collision` or `slug-collision`. QA, including one case where an
    added operation does collide, asserting the finding and that every other URL is unchanged.
    Amended 2026-11-27 for schema pages and the collision exception (ADR 0003, "Stability").
12. **[reader]** An operation with no `operationId` gets the derived id "method, then the path with
    every non-alphanumeric character replaced by `_`" (`get` + `/payments/{id}` gives
    `get_payments__id_`), so that all 41 Clubhouse operations and every GitHub id containing `/`
    have a working page and URL, and two operations that would share an id are resolved exactly as
    section 1.1 of `docs/contracts/guides-contract.md` specifies (a `_2`, `_3` suffix in a defined
    order), with each collision reported as a doctor finding naming both locations. QA, against
    the worked examples in that section.

### Code samples

13. **[reader]** For every operation in all fixtures and each of the 8 languages, the sample passes
    that language's own parser or compiler syntax check. Answers: "Examples are absent or do not
    run". QA. **[judgment]** This needs 8 toolchains in CI; that cost is accepted.
14. **[reader]** For a fixed matrix of request shapes (path, query and header parameters; JSON,
    form-urlencoded and multipart bodies; bearer, basic, and API key in header and in query), the
    sample in each of the 8 languages, run unmodified against the local mock, sends the expected
    method, URL, headers and body, where the expected values are written by hand in the fixture
    and are not taken from the engine's own request. Answers: "Examples are absent or do not
    run". QA, on the request-shape matrix fixture, whose first declared server is the mock, so it
    needs no overlay; the harness refuses to run a sample whose base URL is not the mock's.
    Amended 2026-11-27 to say where the mock's address comes from (ADR 0005, "The local mock").
15. **[reader]** Every sample uses the first server URL declared for its operation, written out
    with each server variable replaced by its default (else its first `enum` value, else left as
    `{name}`), or, where the spec declares no server or the first is relative, the visibly named
    placeholder `https://YOUR_API_HOST` followed by the relative URL; and a visibly named
    credential placeholder such as `YOUR_API_KEY` in the position and with the prefix the security
    scheme requires; and no sample or page in the output contains a real credential or accepts
    one. This holds for a normal build. A mock-server build meets it too, because its overlay
    changes the declared server itself and no option overrides a sample's URL. Answers: "The spec
    itself is wrong" (token prefixes). QA, plus security reviewer. Amended 2026-11-27 to state
    the cases ADR 0005, "What an M1 sample shows", defines.
16. **[reader]** Choosing a sample language on one page shows that language on every other page and
    after a reload and in a new tab, with no server state, and with JavaScript disabled every page
    still shows a readable sample in the default language. QA.

### Agents: Markdown twins and `llms.txt`

17. **[reader, agent]** Every reference page, meaning every operation, tag and schema page, has a
    Markdown twin at the page's path plus `.md` (the page `operations/get-pet/` has the twin
    `operations/get-pet.md`), linked from the page; an operation's twin contains the same
    parameters, schemas, responses and security statement as the HTML page and one sample (cURL),
    with a schema that is a link on the page being a link to that schema's twin; a schema's twin
    contains the same schema as its page and a tag's twin links to the twin of each of its
    operations; no twin contains HTML or navigation chrome; the home page and the doctor report
    have no twin; and `llms.txt` at the unit's root lists every twin exactly once with its title,
    description and a resolving link. Answers: "`llms.txt` is rarely fetched" (per-page Markdown
    carries the agent traffic). QA, by diffing twins against page models. **[judgment]**
    `llms.txt` is table stakes: it must exist and be correct, and gets no effort beyond that.
    Amended 2026-11-27 to say which pages have a twin.
18. **[reader, agent]** Given only the twin of one operation from a mock-server build of Petstore
    and one from a mock-server build of Museum, and the placeholder credential that twin shows, an
    AI agent writes a request that the local mock accepts on the first attempt. DX. Amended
    2026-11-27 to name the build.

### Safety of rendered content

19. **[buyer]** Spec text containing HTML, script, event handlers or `javascript:` URLs, in any
    description, summary, example, enum or name, appears in pages and twins as inert text and
    executes nothing. Standing constraint: tenant content is never executed. QA, on the
    hostile-content fixture; security reviewer sign-off is required. Amended 2026-11-27: the
    fixture is QA's hostile-content fixture, not one of the `broken` set.

### Determinism and static output

20. **[buyer]** Building the same spec and patch twice, on two machines, yields byte-identical
    pages, twins, `llms.txt`, samples and doctor report, with no timestamps or random ids in the
    output. QA.
21. **[buyer]** The built portal is a directory of static files that works from a plain file server
    with no application server, at the root, under a subpath such as `/docs`, and under a subpath
    with a unit prefix such as `/docs/payments/v2`, with every internal link, asset and twin URL
    resolving in all three, and with twin and `llms.txt` links written relative to the file they
    are in. Decision: a portal may hold several APIs and versions, each one unit (ADR 0002, "The
    unit"; ADR 0006, "Units"). Standing constraint: static export;
    decision: subpath hosting. QA. **[judgment]** Checking the subpath now is cheaper than
    retrofitting it in M4.

### Accessibility

22. **[reader]** On a fixed sample of pages (a simple operation, a `hard-schemas` operation, a
    schema page, a tag index, the doctor report), an automated WCAG 2.2 AA audit reports zero
    violations, and navigation, the language switcher, variant switchers, schema expanders and
    copy buttons are all operable by keyboard alone with a visible focus indicator. QA, with a
    manual screen-reader pass by UX on the same pages. **[judgment]** AA is our bar; the brief does
    not set one. Amended 2026-11-27 to add a schema page to the sample.

### Performance on a very large spec

The reference machine is a 4-core, 16 GB Linux CI runner (ADR 0003, "Performance").

23. **[buyer]** `large/github-ghes.json` (908 operations) and `large/stripe.json` (612) each build
    to a complete portal, every operation present, with the engine pass alone under 60 seconds
    and inside Node's default heap, with no `--max-old-space-size`, and with the full build within
    5 minutes, on the reference machine. QA. The engine pass is `parseDocument`, `applyFixes`,
    `buildModel`, `diagnose` and `buildPortalBundle` in one process, timed around the calls,
    without reading or writing files. The full build is one `ezdp` command from start to a
    complete export directory, without installing dependencies, `fetch.sh` or the sample
    toolchains. Standing of each threshold, from ADR 0003:
    - **60 seconds: confirmed by the architect.** What was measured is parsing only, about 2
      seconds a fixture; the rest of the pass does not exist yet and is expected to be linear in
      the model. That expectation is inference.
    - **Default heap: a rule, added 2026-11-27.** A pass that needs a raised heap fails.
    - **5 minutes: a target, not yet measured.** It is still the pass mark. If Stripe misses it,
      `pageSchemas` is lowered first; changing the figure takes a recorded decision in this file.

    Amended 2026-11-27 to name the fixtures, add the heap rule and state what is measured.
24. **[reader]** On `large/github-ghes.json`, no operation page transfers more than 500 KB
    compressed excluding fonts, measured as the sum, over the page's HTML file and every script
    and stylesheet that file loads, of each file's size under gzip at level 6, taken from the
    export directory with nothing cached; no page embeds the whole spec; and the navigation
    listing all 908 operations responds to scroll and click without a visible stall on a
    mid-range laptop. QA for the first two clauses, DX for the third. The 500 KB threshold is
    confirmed (ADR 0006, "Page weight"). Amended 2026-11-27 to say how it is measured.

### End to end

25. **[reader]** Starting from the home page of a mock-server build of Petstore with no prior
    knowledge of the API, a developer finds an operation, finds what credential it needs, copies a
    sample in a language of their choice, and has it run against the local mock exactly as copied,
    with no edit; and every sample of that build differs from the same sample of the normal
    Petstore build in the server URL and in nothing else. DX, repeated in at least three of the 8
    languages, for the first part; QA, by diffing the two builds, for the second. Amended
    2026-11-27. It used to say "after changing only the credential placeholder". As designed the
    mock accepts the placeholder text itself as the credential, so nothing is changed, and the
    sample a real reader copies points at the real server, not the mock. The diff is what ties the
    two together: on a normal build the one thing a reader replaces is the credential
    placeholder. M1 does not test that step or any call to a real server; see "Not tested by these
    criteria".

### Published spec

### Fixes that no longer apply

28. **[buyer]** A patch whose `test` no longer holds, or whose path is gone, is reported as not
    applied, naming the fix, while the build completes and every other patch is applied. ADR 0004,

    at least two that still apply.

### Callable servers and the allowed-hosts fix

These three follow the security review of 2026-11-27 (F1 and rulings 1 to 4). They protect the
reader's credential in M2; in M1 what can be observed is the doctor's output and the CLI.

29. **[buyer, reader]** For every row of the worked-examples table in ADR 0004 the doctor gives
    that row's result, and a fix only where the row says one is offered, against the pinned Public
    Suffix List snapshot; with `publicSuffixes: null` every host variable without an `enum` is
    `server-not-callable`; and a variable with an empty `enum` is `server-not-callable` with no
    fix. QA; security reviewer sign-off is required.
30. **[buyer]** A provenance test recomputes the SHA-256 of the vendored Public Suffix List file

## Not tested by these criteria

Known gaps, written down so that nobody reads a passing M1 as covering them. Each is the product
manager's reading of the ADRs, not a test result.

- **A sample value against a `pattern`.** The engine never runs a tenant's regular expression
  (ADR 0003, "Schema validation"), so a synthesized value for a string with a `pattern`, or with
  a format outside the nine listed, may not satisfy it, and a real API may reject the sample.
  Criterion 7 reports such a value as not checked; it cannot make it right.
- **Replacing the credential placeholder.** Criteria 14, 18 and 25 run samples with the
  placeholder text as the credential. No M1 test puts a real-looking key into a sample, so
  quoting or escaping of a key with unusual characters is first exercised in M2.
- **Any call to a real server.** M2.
- **That a `synthesis-failed` schema truly admits no value.** Criterion 7 asks for a written
  reason per case in the committed fixtures. For the fetch-only fixtures nobody reviews them.
- **Webhooks and callbacks listed as not rendered.** ADR 0004 names the two findings and the
  corpus has a fixture for each (`oai-webhook-example`, `oai-callback-example`), but no criterion
  asserts the findings appear. Proposal D in `docs/product/user-stories.md`; to be decided before
  M1 closes.
- **Page weight outside GitHub operation pages.** Criterion 24 measures operation pages of one
  fixture. Schema pages, and Stripe's operation pages with 32 schemas in place, are not measured.
- **Budgets.** That a small spec which expands to an enormous example is cut and reported
  (`budget-exceeded`) is a security review gate in the kickoff, not a criterion here. Criterion 3
  checks only that no fixture is truncated.

## Definition of done

M1 is complete when all of the following are true. This follows `CLAUDE.md`, "Rules for using the
team".

1. **PM criteria checked.** The product manager has marked each of the 31 criteria met, not met or
   not checked, with what was looked at, against the built portals, not a summary. No criterion is
   "not checked". Any "not met" is either fixed or moved out of M1 by a recorded decision in this
   file.
2. **QA has run the tests.** The QA engineer has run the automated suite on all fixtures on CI and
   reports the result per criterion. Criteria 13 and 14 have run with all 8 toolchains. Criterion
   23 reports the measured times and that no heap flag was set.
3. **DX reviewer has used the result.** The DX reviewer has used the built Petstore, Museum and
   GitHub portals and completed criteria 18, 24 (third clause) and 25. For 18 and 25 the Petstore
   and Museum portals are mock-server builds; the DX reviewer also opens the normal builds.
4. **Security reviewer has signed off** on criteria 15 and 19, since M1 renders tenant content, and
   on criteria 29 and 31, since they decide which servers the M2 proxy may send a reader's
   credential to. The sign-off on 29 covers the details the architect added to make the host rule
   decidable, which the third review did not see.
5. **Standing constraints hold**: the engine performs no I/O, and takes the Public Suffix List as
   an input and does not read it (29, 30); core pages are static (criterion 21); tenant content is
   not executed (19); no credential is stored or logged, which in M1 means none is ever accepted
   (15).
6. `docs/product-brief.md` is updated with any decision M1 changed.

## Product questions

Settled on 2026-11-27:

1. **Which 8 languages?** cURL, JavaScript (`fetch`), Python (`requests`), Go, Java, C#, PHP, Ruby.
   The HTTP client each emitter targets is listed in ADR 0005.
2. **Swagger 2.0** is out for now. It is rejected with a clear message.
3. **Derived operation ids.** The rule is section 1.1 of `docs/contracts/guides-contract.md`, which

   the build.

   the CLI's check are criteria 8, 10, 29 and 31. Enforcement at the proxy is M2.

   2.0, vendored with its licence text. Builds pass the snapshot, not `publicSuffixes: null`; the
   `null` mode stays supported and tested (criterion 29).
